# 卡顿排查与优化

本轮针对历史任务增多、执行日志变长和并发任务状态更新时的重复开销，不裁剪历史记录，不降低落盘可靠性，不新增运行时依赖。

## 已处理的热点

| 链路 | 原有开销 | 优化与回归证据 |
| --- | --- | --- |
| 任务 / Issue 广播 | 一次状态变化触发任务列表、App 的 Issue 列表和看板 Issue 列表三次全量 IPC | 广播携带完整对象时增量落位；稳态 55 次广播产生 0 次额外全量读取。首载、显式刷新和必要对账仍取快照 |
| 首载与刷新竞态 | 广播可能反复取代在途快照；旧快照可能覆盖新状态 | 在途广播缓冲重放；首载 20 次突发广播仍仅一次任务列表读取；卸载作废读取。只收到 Issue 广播的停泊建单若不在旧快照中，读完成后补一次对账 |
| 执行日志 | 每条广播立即合并历史并触发渲染；未变化的 Markdown 反复解析 | 16ms 或 64 条事件触发一次合并；1000 条广播完整保留，仅 16 次合并。相同 Markdown 文本跳过组件重渲染 |
| 单任务日志读写 | get、append 和恢复副本暂存逐个计数所有历史任务的日志 | 只计目标任务；暂存恢复副本不扫描日志。128 个任务、64 次追加的计数调用由 8256 次降到 128 次 |
| Issue / Run / Comment 投影 | 每个任务反复 find/filter 所有 Issue、Run、报告及父任务 | 建立本次投影内的索引，保留最早匹配优先级；2000 个任务的样本为 0 次 find/filter 谓词访问、25000 次 Map.get，并正确建立 1000 条父子链接 |

以上数字来自临时数据和假桥驱动的自动化回归，不代表真实 Electron 会话的帧率或总耗时提升比例。Issue 投影样本单次约 32ms，随机器和数据形态变化，不以固定耗时作为测试门槛。

## 保留的安全边界

- 每次主进程事务仍在共享存储锁内读取最新索引，不使用无失效的跨请求任务缓存。
- 公共 transaction、list、启动恢复和 flush 仍全量校正日志计数。
- 保留接受事件时的恢复副本、持久化确认顺序、陈旧 run/owner 拒写及删除墓碑；补测批量追加的身份拒写和恢复副本只回放一次。
- Issue 投影保留人工状态、评论、旧报告认领与歧义处理；指纹相同也读取锁内最新 Issue 数据，未确认投影不会被跳过。
- 看板刷新只由最新请求结算 loading/error，较早读取晚到不会让同步状态卡住。

## 验证入口

```bash
npm run smoke:performance
npm run typecheck
npm run build
npm run smoke:stage6
```

`smoke:performance` 包含真实 React hook/看板渲染竞态、日志批处理、任务日志计数与 Issue 大样本投影四组测试，也已接入 `smoke:all`。

## 仍需关注的边界

任务索引解析、投影指纹序列化、数据克隆和可靠落盘仍存在随数据量增长的线性开销。Windows 争锁时的同步进程身份探测也可能延迟主线程；本轮先缩短锁内重复工作，未通过删除锁或取消 fsync 掩盖卡顿。若真实会话仍出现长时间停顿，应记录当时任务数、并发数、所在页面和操作，再针对性采样主进程与渲染进程。
