## 1. 需求边界

### 1.1 已确认的用户要求

| 项目 | 要求 |
| --- | --- |
| 页面 | 需要独立会议详情页，但沿用普通 Issue 的页面骨架和视觉风格，不另造一套陌生界面。 |
| 对话 | 会议成员在同一个会议 Issue 中轮番发言，每个气泡明确显示发言人。 |
| 内部详情 | 通过现有右侧分栏查看所选队长的内部执行、调查和日志。 |
| 侧栏选择 | 默认固定用户选择的队长，不随发言自动跳走；可以提供“跟随当前发言者”选项。 |
| 公开归属 | 内部会议执行不能散落成看板上的独立卡片，应从会议主 Issue 内查看。 |
| 生命周期 | 用户点击主页面“停止”，再点击“删除任务和日志”，应作用于整场会议，不能只处理普通容器任务。 |
| 协作 | 必须能看见讨论和质疑，也需要说明不同平台的 agent 实际如何收到彼此的发言。 |
| 工作方式 | 先收集现况、讨论和规划，经确认后再实施。 |

### 1.2 本方案提出、用户批准施工采用的技术与交互选择

1. 正常创建会议后自动启动；创建时展示“正在准备”，失败时明确原因并提供重试，而不是进入普通 Issue 后再手动启动 agent。
2. 将会议成员会话与长期“队长办公室”分开，使用会议范围内的成员会话；办公室继续用于独立咨询。
3. 公开气泡先显示实名占位和运行状态，完成后发布正式发言；工具调用、草稿和调查过程放在成员侧栏。
4. 宿主统一装配、转发和留存公开上下文；质疑由提出者复核，最终纪要经过成员重新确认。

本方案不新增多会议并发能力，不引入外部聊天服务、数据库或主进程运行时 npm 依赖。

## 3. 总体结构：公开 Issue、会议调度、内部执行分层

```text
公开会议 Issue
  ├─ 会议专属详情页：议题、成员、实名发言、质疑、纪要
  ├─ 右侧成员面板：固定所选成员 / 可选跟随发言者
  └─ 会议控制器（宿主）
       ├─ 本会议成员会话 A → 平台后端 A
       ├─ 本会议成员会话 B → 平台后端 B
       └─ 内部调查任务 → 可并行，结果先回给所属成员

长期队长办公室 → 独立咨询，不归本会议停止或删除
```

会议是编排与归属边界，Issue 是用户的公开入口，内部任务仍是可观测的执行记录。不是把所有平台塞进同一个 CLI 会话，也不是让它们自动读取一个共享聊天窗口。

### 3.1 主 Issue 与会话归属

- 新建会议默认拥有一个会议专属主 Issue。保留必要的容器兼容记录，但不把它分配给普通 agent 执行。
- 新成员会话使用 `(meetingId, agentId)` 范围键，记录其工作目录和执行关联；不复用其他会议或咨询办公室的隐含目录。
- 内部任务增加受宿主控制的会议归属信息，例如 `meetingId` 和 `container/member/investigation` 角色；字段名称在实施时定稿。
- 调查、委派及重试在创建时继承可信归属，不能从模型输出的任意字段取得取消或删除权限。
- 正式发言关联到具体成员会话及 Run/回合；停止通过归属登记表找出全部在途执行，不依赖一棵可能缺节点的 UI 树。

**重要限制：不能直接把成员会话变成普通容器的 `parentTaskId` 子任务。** 当前 `runner.spawnInvestigateChild` 会拒绝已有父任务的再次调查，其他流程也依赖调查父子语义。会议归属应先与普通执行父子关系解耦；若要调整父子关系，须同时证明委派、调查、预算、日志和 worktree 语义不回归。

### 3.2 公共可见性

- 保留完整内部执行目录供调度、成本统计、日志和侧栏使用，不从底层全局列表直接删掉内部任务。
- 公共看板、Issue 列表、搜索、最近访问和任务选择器统一使用可见性判断，避免各自补一处过滤。
- 新会议内部任务按可信归属隐藏；旧记录兼容 `suppressIssue` 和办公室标识，不能因隐藏父节点缺失而变成顶层卡片。
- 调查从会议成员侧栏打开；内部任务事件不得自动把主页面导航切到普通任务详情。
- 纪要中的“行动项”不等于内部调查。若需要另建正式交付 Issue，须明确审批并展示来源链接，不能会议运行中悄悄冒出。

### 3.3 稳定导航

- 会议详情以稳定的 Issue/meeting 标识解析，不以“普通 task 必须存在”为前提。
- 从看板、Issue 列表、搜索和历史记录进入同一会议页面；普通 Issue 仍使用原页面。
- YOU-384 这类缺少容器任务的历史会议应能查看现存记录，明确标示缺失部分，而不是空白或启动一个新普通任务。

## 4. 跨平台通信：宿主转发同一份公开事实

### 4.1 当前机制与缺口

跨平台 agent 并不直接互相通信，而是宿主把文本加入下一位成员的输入。正式会议发言按阶段顺序执行，内部调查可以并行；评论出现在共享 Issue 上，不意味着其他 agent 已收到它。

已安装旧循环主要分段转发：报告者收到议题，质疑者收到报告，报告者收到解析出的质疑，综合成员收到部分处理结果。这不等同于每位成员都看过完整、最新的公开讨论。工作区尝试性修正需要重新审查、纳入正式模型和回归测试。

### 4.2 下一版通信约定

1. **公开事实源**：保存完整正式发言、用户插话、质疑及处理记录；内部工具日志不自动成为公开发言。
2. **统一上下文包**：宿主为每次发言组装会议议题、当前轮次/阶段、身份职责、版本化公共历史、未解决质疑和最新用户要求。
3. **可追溯投递**：记录本次输入使用的公共上下文版本和发言范围，诊断时能回答“这位成员当时收到哪些内容”。不默认在公开页展示原始提示词或敏感工具日志。
4. **控制上下文长度**：已稳定历史可生成带来源的摘要；未解决质疑、最新修订与待确认纪要优先保留。超限明确记录压缩/省略范围，不无声截成最前面若干字符。
5. **后端差异**：支持持久会话的后端在会议范围内复用；无持久会话的后端由宿主每次重新装配必要上下文，不假设所有 CLI 都支持相同恢复机制。

### 4.3 讨论与收敛

- 保留现有顺序阶段，不为营造热闹强行让所有成员同时向主时间线输出。
- 阶段标签与成员职责分开：同一报告者可以在“答辩”阶段发言，不能把一个成员的固定角色简单显示成“答辩”。
- 质疑有稳定 ID、提出者、正文、严重程度、答复及复核状态。答辩者不能仅靠自己声明将其关闭。
- 复核由原提出者依据最新修订确认；不同意见保留为记录，不用格式解析失败或空响应冒充同意。
- 最终纪要生成后重新送达相关成员确认；有新阻断项则继续讨论或明确结束为未达成一致，不能沿用旧报告的同意状态。
- 用户插话立即进入公开时间线，在下一个安全阶段边界送达成员；本轮已发出的请求不能伪装成已经收到插话。
- 调查结果先回到所属成员，再由其公开引用或归纳；普通派单不会因为属于会议就自动变成另一位公开发言人。

| 数据 | 用途 |

- 首版不把全部 CLI stdout 流到公开区；内部流由既有事件日志显示。若后续公开正文需要流式展示，应另定义结构化事件边界。
- Issue 评论仅作为兼容镜像，以来源发言 ID 去重；镜像失败可重试，不能影响权威发言读取，也不能重新触发普通 `@agent` 执行。
- 存储沿用现有持久化方式，记录版本迁移、写入一致性与失败恢复；完整正文不能无界塞进每次整体读写的热索引。

## 6. 页面与右侧分栏

### 6.1 页面结构

```text
会议主 Issue：标题 / 状态 / 轮次与阶段 / 停止 / 删除任务和日志
成员栏：姓名、角色、状态；点击打开右侧
────────────────────────────────────────────────────────
公开时间线                              右侧成员详情（可关闭）
  姓名 · 平台 · 阶段 · 时间               所选姓名 · 固定/跟随开关
  正式发言 / 正在准备 / 失败原因           当前或选定发言的执行
  质疑与答复                             调查列表、工具事件、日志
  用户插话                               历史执行切换
  最新纪要及确认状态
底部：用户插话输入与当前送达状态
```

- 保留普通 Issue 的标题区、时间线、输入区和现有 `SideDock` 交互，新增会议专属组合页面，不复制一份完整 `TaskDetail`。
- 每个气泡在正文生成前就显示发言者；颜色可辅助区分，但姓名不能只靠头像、颜色或顶部当前成员提示表达。
- 页面状态区区分当前公开发言者与内部并行调查，不让“某成员忙碌”误导为“正在公开发言”。
- 宽度不足时右侧沿用现有折叠/覆盖方式，优先保留正文可读性；不新增独立弹窗作为唯一入口。

### 6.2 固定与跟随行为

- 初始不自动抢开侧栏；点击成员或某条发言后打开，按会议 root 保存选择。
- 默认固定所选成员。点击发言时优先定位该条关联的 Run；点击成员时显示该成员当前执行或最近一次执行。
- 固定 A 后，即使 B 开始发言，侧栏仍显示 A；只更新 A 自己的运行内容和列表。
- “跟随当前发言者”由用户显式开启，仅在正式发言阶段切换，不跟随调查任务或工具调用跳动。
- 跟随开启时，用户手动选择另一成员会关闭跟随并进入固定模式，避免马上被下一次事件抢回。
- 切换页面、关闭再打开侧栏后，恢复本会议的选中成员和模式；状态不能串到其他会议或普通 Issue。
- 成员面板复用 `WorkerPane` 的日志渲染能力，但隐藏普通任务的独立开始/删除等不适用于会议的操作。

### 6.3 视觉与设计确认

沿用 `tokens.css` 的主题变量和明暗主题：当前深色基底约 `#101113`、抬升面 `#17181b`、强调色 `#3dbfae`、正文 `#e9eaec`。沿用 Segoe UI / Microsoft YaHei、Cascadia Code / Consolas、4px 间距网格、6px 控件与 8px 卡片圆角。

正式 UI 接线前先提交一个包含“实名时间线 + 固定成员侧栏”的 v0 供用户确认；不先做完全部视觉再讨论，也不新增图片或 UI 框架。

## 7. 创建、停止与删除语义

### 7.1 创建与启动

- 会议信息与主 Issue 归属先落盘，再由统一会议入口启动；重复点击或渲染重挂载不能启动第二次。
- 普通任务开始、自动 assignment、重试和快捷操作必须识别会议容器：转入会议控制或明确拒绝，不能只依赖按钮隐藏。
- 创建失败、初始化失败和通信失败分别可见；创建后未启动不能表现成正在开会。
- 保留当前单活跃会议限制；咨询与会议执行隔离不代表开放多会议并发。

### 7.2 停止整场会议

1. 在任何 await 之前持久化停止意图并使当前调度代次失效，立即阻止新发言、调查、重试和派单。
2. 通过会议归属表停止在途成员执行及其调查/委派后代，释放排队请求、等待项、会话锁和定时器。
3. 在初始化、排队取出、发送前、发送返回后及发布结果前检查代次和删除标识；晚到结果不能恢复任务或启动下一位成员。
4. 等待后端确认终止，必要时按现有适配器能力安全处理该执行拥有的进程树；不能仅把数据库状态改为 cancelled。
5. 终止确认前显示“正在停止”；超时/失败保留任务与归属并明确报错，允许重试，不能显示假成功。

重复停止幂等。停止不影响其他会议或独立咨询办公室。取消后只有用户显式重新启动才能建立新代次，不能被 `runner.followUp` 的恢复能力自动复活。正式失败或结束也需要收拢仍在途的会议内部工作，不能留下后台孤儿任务。

离开详情页、关闭侧栏或浮层只是关闭视图，不等于停止；UI 必须说明会议仍在运行。暂停保留阶段边界语义，不能冒充已经终止当前 CLI。

### 7.3 删除任务和日志

- 删除先写入防重入标记，再停止并等待全部已知会议执行退出；停止失败时不破坏可诊断记录、不把会议从视图中假删除。
- 删除本会议拥有的成员/调查任务、执行日志、公开发言、纪要、镜像评论、导航引用及会话恢复关联；工作目录内用户源文件不在“日志删除”范围。
- 新建的会议专属主 Issue 可以随会议删除；挂接既有普通 Issue 或归属不明的历史记录，仅删除能证明属于会议的内容，保留无关历史并说明原因。
- 跨多个存储的清理使用可恢复的删除进度，重复调用或重启可继续，不要求假装一次原子删除。
- 删除期间晚到事件、评论和执行回调不能重新创建记录；完成后所有公共入口消失，侧栏缓存清空。
- 已批准独立交付的行动项按其独立归属保留，不作为会议内部任务连带删除；确认框说明保留范围。

## 8. 旧数据与兼容

- 不把共享办公室整条历史归给某一个会议，更不能删除整个办公室来满足某场会议的删除操作。
